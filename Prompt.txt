Good catch — this is the real crux of it, and I dug into the schema to confirm the right architecture. Here's what I found and why it changes the design:

**The schema already has a derivation trigger you're not using — `PAY_EMP_PF_HDR_NEW`**

This is a `BEFORE INSERT OR UPDATE ... OF <open/trans/int columns>` trigger already sitting on `PAY_EMP_PF_HDR`. It does exactly this:
```
close_bal := open_bal + trans_in_amt + close_int_bal - trans_out_amt
```
...and it **already** skips this whenever `AQ_PROCESSED IN ('F','R')`, raising `-20001` if someone tries to touch a frozen/finally-sanctioned year. There are two more active HDR triggers (`TRG_PAY_EMP_PF_HDR_A`, `A1`) that guard against balances going negative. So closing-balance derivation and F/R protection are **already centrally handled** — your DTL trigger shouldn't be doing that math itself (it currently duplicates it, which is part of why drift creeps in).

**Your actual problem, correctly diagnosed:** `EMPLOYEE_SUBS_TRANS_IN_AMT` / `..._OUT_AMT` / `VPF_TRANS_*` on the header are being maintained by **delta math** (`NEW − OLD` on the touched row). Delta math is only correct if the header's current value is already trustworthy. If it was ever hand-corrected (via `PF_HDR_DATA_FIX`, which I also found in your schema — a reconciliation procedure that already exists for exactly this "header vs. actual doesn't match" situation) or if a past bug wrote a wrong value, every future delta update just carries that error forward forever. Delta math can never self-heal. **Only a full re-sum from `PAY_EMP_PF_DTL` is self-healing** — which is why you tried it, and why it hit the mutating-table wall.

**Best solution: full re-sum (self-healing) done safely, then let existing triggers cascade it**

Architecture:
1. DTL compound trigger, `AFTER EACH ROW`: ensure the year's header row exists (unchanged), then just record `(emp_num, from_year)` as touched — no math here.
2. `AFTER STATEMENT` (table no longer mutating): for each touched key, **skip entirely if that header's `AQ_PROCESSED IN ('F','R')`** (your requirement), then set `TRANS_IN_AMT`/`TRANS_OUT_AMT`/`VPF_TRANS_*` to the authoritative `SUM(PAY_EMP_PF_DTL)` for that year — always correct regardless of any prior drift.
3. That `UPDATE` naturally fires `PAY_EMP_PF_HDR_NEW`, which derives `close_bal` correctly — no duplicate close-bal logic needed in the DTL trigger at all.
4. Cascade forward year-by-year (not bulk-delta like before): for each subsequent year that exists and isn't F/R, set its `OPEN_BAL := previous year's now-correct CLOSE_BAL`, which again fires `PAY_EMP_PF_HDR_NEW` to derive that year's `close_bal`, and the loop continues. This stops cleanly at the first frozen year, and self-heals every year in the chain rather than propagating a possibly-wrong delta.

**Why this is the right level to fix it at, not the HDR trigger:** you can't move the re-sum logic into a trigger *on* `PAY_EMP_PF_HDR` fired from within the same DTL statement — it would still be nested inside the original DTL DML's execution, so `PAY_EMP_PF_DTL` would still be "mutating" from Oracle's point of view, and you'd hit the same ORA-04091. The re-sum has to happen in `AFTER STATEMENT`, which only a compound trigger (on the DTL table) gives you.

**Answering your specific concerns:**
- *"What if DTL already stored a wrong value and closing bal was data-fixed separately?"* — Handled. The re-sum reads `SUM(PAY_EMP_PF_DTL)` fresh every time, so it self-corrects regardless of what history led to today's numbers. It doesn't trust or carry forward any prior stored total.
- *"Update correct closing in current and opening in next table, also next year records"* — Handled by `cascade_forward`, walking year-by-year (not one bulk delta jump), each year re-deriving from the actual previous year's close balance.
- *"Non-frozen, non-F/R records only"* — Both the re-sum and every step of the cascade check `AQ_PROCESSED NOT IN ('F','R')` and stop/skip accordingly; frozen years are left untouched, matching `PAY_EMP_PF_HDR_NEW`'s own rule.

**One recommendation:** since you already have `PKG_PAYROLL_SUPPORT_EXT.PF_HDR_DATA_FIX` for manual reconciliation, once this trigger is live you likely won't need that procedure for *new* drift going forward — but keep it for any pre-existing bad data from before this fix, run once as a one-time cleanup pass.
